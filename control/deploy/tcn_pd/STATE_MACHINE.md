# TCN+PD Deploy 最简内部状态机设计

## 1. 文档状态

本文定义 `control/deploy/tcn_pd` 采用的最简内部状态机。

它是目标设计，不是对当前 C++ 实现的描述。当前实现仍包含 `SHUTTING_DOWN`，并会在
清理时覆盖故障原因；代码和测试需要在后续编码步骤中按本文对齐。

本文只定义 Deploy 进程内部行为。外部控制状态机、IPC、CAN、电机使能、急停和硬件
安全均不属于本文范围。

## 2. 核心边界

Deploy 状态机只在 Deploy 进程存在期间存在：

```text
进程启动 = 创建一套全新的 Deploy 运行实例
进程退出 = 销毁全部 Deploy 内部状态
进程不存在 = 不存在可查询、恢复或持久化的内部状态
```

因此停止是一个导致清理和进程退出的事件，不是一个需要长期保存的内部状态。

初始化是创建 Runtime 的事务过程。只有模型、配置和 ONNX Runtime Session 全部初始化
成功后，内部状态机才从 `WARMUP` 开始。初始化失败时不创建可运行状态机，而是记录启动
错误、执行同一套清理并以非零状态退出。

## 3. 状态集合

内部只保留三个状态：

| 状态 | 含义 | 输出约束 |
|---|---|---|
| `WARMUP` | 正在建立启动所需的有效传感器历史 | 力矩和动作严格全零 |
| `READY` | 本次 `step()` 返回有效控制命令 | 允许输出 TCN+PD 结果 |
| `FAULT` | 内部故障已锁存，等待 owner 线程清理退出 | 力矩和动作严格全零 |

不设置以下状态：

- `UNINITIALIZED`：它属于 Runtime 构造前置条件，不属于运行状态；
- `INITIALIZING`：初始化是同步创建事务，不需要外部观察；
- `SHUTTING_DOWN`：当前清理是同步操作，没有可观察的异步关闭阶段；
- `STOPPED`：清理完成后进程立即退出，内部状态机已经不存在；
- `PAUSED`、`DISABLED`、`RESETTING`：这些能力不在首版 Deploy 范围内。

## 5. 事件与转换

| 当前状态 | 事件 | 下一状态或结果 | 行为 |
|---|---|---|---|
| 无状态机 | 初始化成功 | `WARMUP` | 历史和计数器从零开始 |
| 无状态机 | 初始化失败 | 进程退出 | 保存启动错误、统一清理、退出码 2 |
| `WARMUP` | 第 1 至 150 个有效输入 | `WARMUP` | 更新历史，输出严格全零 |
| `WARMUP` | 第 151 个有效输入 | `READY` | 写入该帧后推理并返回第一条命令 |
| `WARMUP` | 内部错误 | `FAULT` | 锁存根因并返回严格零输出 |
| `READY` | 有效输入 | `READY` | 返回 TCN+PD 命令 |
| `READY` | 内部错误 | `FAULT` | 锁存根因并返回严格零输出 |
| `FAULT` | owner 处理终止 | 进程退出 | 统一清理、退出码 3 |
| `WARMUP/READY` | 可处理的停止请求 | 进程退出 | 统一清理、退出码 0 |

`FAULT` 不提供恢复转换。恢复只能结束当前进程并启动一个全新的进程。

## 6. 输出不变量

Deploy 必须满足：

```text
state == READY  <=>  当前 StepResult 中的控制命令有效
state != READY  =>   target_torque_nm[4] 全零且 action[4] 全零
```

具体要求：

1. `WARMUP` 的每一次返回都必须严格为浮点全零；
2. 第 151 次有效调用先写入当前帧，再推理并转入 `READY`；
3. `FAULT` 必须在释放资源之前先使输出失效；
4. 输入 NaN/Inf、推理错误或中间非有限值不得泄漏上一周期输出；
5. 进程停止不得重复发送最后一条有效命令。

## 7. WARMUP 语义

`WARMUP` 只统计成功通过有限值检查并写入历史的 `sensor32`。计数依据是有效输入帧数，
不是进程运行时间。

固定时序为：

```text
valid step 1..49:    TCN 历史未满，输出零
valid step 50..149:  TCN 历史已满，但控制输出仍为零
valid step 151:      使用包含当前帧的最近 50 帧完成推理，进入 READY
```

TCN 是无隐藏状态的因果网络，因此不要求在第 50 至 149 帧持续执行并丢弃推理结果。
首版可以只在第 151 帧执行首次正式推理，以减少无意义计算；这不改变历史或输出语义。

任何无效输入都进入 `FAULT`，不跳过该帧继续预热，避免 Deploy 与外部周期计数产生不同
理解。

## 8. FAULT 语义

以下情况进入 `FAULT`：

- 运行期输入包含 NaN/Inf；
- TCN 预处理、推理、反归一化或 PD 结果产生非有限值；
- ONNX Runtime 推理异常；
- 内部历史或计数器不一致；
- 其他会使当前输出语义不可信的内部错误。

模型包、配置、SHA-256 或 tensor 接口在启动时失败，属于初始化失败；它们使用相同的错误
记录和清理机制，但不会产生一个可运行的 `FAULT` Runtime。

进入 `FAULT` 时按固定顺序处理：

1. 将本次 `StepResult` 的目标力矩和动作设置为严格全零；
2. 锁存第一个故障的 `fault_code` 和 `fault_message`；
3. 后续错误不得覆盖第一个根因；
4. 将零输出和 `FAULT` 返回给 owner；
5. owner 记录诊断并立即调用统一清理；
6. 进程以非零状态退出。

`FAULT` 是短暂但有意义的终止状态：它用于保证一次明确的零输出和可诊断的根因，不用于
等待人工恢复。

## 9. 停止与统一清理

以下路径必须调用同一个幂等 `cleanup()`：

- 正常停止请求；
- `SIGINT`；
- `SIGTERM`；
- 运行期 `FAULT`；
- 部分初始化后的失败；
- Runtime 析构兜底。

信号处理器只能设置原子停止标志。创建和使用 ONNX Runtime Session 的 owner 线程读取该
标志后执行清理；不得从异步 signal handler 或其他线程直接释放 Session。

统一清理顺序为：

1. 使控制输出立即失效并归零；
2. 禁止新的 `step()` 进入；
3. 清空 TCN 历史、计数器和输入输出缓冲；
4. 释放 ORT tensor、MemoryInfo、Session 和 Env；
5. 释放模型配置；
6. 保留退出前所需的故障和停止诊断；
7. 返回 owner，由进程按原因选择退出码。

`cleanup()` 必须允许重复调用，但只执行一次资源释放。

## 10. 故障与停止原因分离

生命周期状态和终止原因不得共用一个字段。至少保留：

```text
state
fault_code
fault_message
stop_reason
warmup_valid_steps
```

正常停止示例：

```text
fault_code = NONE
stop_reason = SIGTERM
exit_code = 0
```

故障停止示例：

```text
fault_code = MODEL_INTEGRITY
fault_message = "TCN SHA-256 mismatch"
stop_reason = INITIALIZATION_FAILURE
exit_code = 2
```

调用清理不得把故障根因改写为 `SHUTDOWN_REQUESTED`，也不得清空故障消息。

建议的进程退出码：

| 退出码 | 含义 |
|---:|---|
| 0 | 正常停止、SIGINT 或 SIGTERM |
| 2 | 初始化或模型包失败 |
| 3 | 运行期故障 |
| 64 | 命令行参数错误 |

## 11. 强制停止的边界

“所有停止走同一清理”只适用于进程有机会执行用户态代码的停止方式：正常请求、
`SIGINT`、`SIGTERM` 和内部故障。

以下情况无法执行 Deploy 清理：

- `SIGKILL`；
- 断电；
- 内核崩溃；
- 进程所在硬件失效。

因此外部电机层必须独立实现通信超时归零、心跳丢失停机、硬限矩和急停。Deploy 内部状态
机不能替代这些机制。

## 12. 明确不实现的能力

首版状态机不实现：

- 进程内 `reset()`；
- 从 `FAULT` 恢复；
- 暂停和继续；
- 模型热更新；
- 运行时重新初始化；
- 外部使能或 ARM 状态；
- 外部安全状态机；
- 跨进程状态持久化。

这些能力若未来确有需求，应由新的外层状态机处理，不扩张本 Deploy 黑箱的三状态模型。

## 13. 当前实现对齐项

后续编码只需完成以下状态机调整：

1. 从公开 `State` 删除 `kShuttingDown`；
2. 初始化成功后才暴露处于 `WARMUP` 的有效 Runtime；
3. 将 shutdown 作为同步终止操作，而不是可长期查询的状态；
4. 将 `fault_code/fault_message` 与 `stop_reason` 分离；
5. 保留首个故障根因，清理时不得覆盖；
6. 主循环检测 `FAULT` 后自动执行统一清理并非零退出；
7. 更新测试，验证非 `READY` 输出严格为零和所有停止路径使用同一清理；
8. 第 150 个有效输入仍严格为零，第 151 个有效输入首次输出命令。
